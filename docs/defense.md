# 방어

원래 문제: **주민이 어느 순간 다 죽어 있다.** 이 문서가 그것을 해결한다.

체감 순서대로 구현한다. 야간 대피 → 경보 상태 → 민병대 → L2 습격 공식. 앞의 둘만으로도 사망률이 크게 떨어진다.

## 야간 대피 — 가장 싸고 효과가 크다

바닐라 주민은 밖에 갇히면 그냥 죽는다. 몰살의 가장 흔한 원인이다.

- 일몰 `curfewLeadTicks`(기본 1200 = 1분) 전에 귀가를 시작한다
- 마지막 주민이 들어오면 문을 닫는다
- 실외에 남은 주민은 **가장 가까운 실내**로 간다. 자기 집이 아니어도 된다
- 실내 판정은 **`AnchorSet.shelters`** 를 본다. 월드 스캔이 필요 없다

> **구현 노트 (M1).** `BUILT` 셀은 M3에서야 채워진다. 그래서 `shelters`는 추상을 하나 거친다 — 플롯이 있으면 플롯을, 없으면 **등록된 바닐라 마을의 침대 POI**를 쓴다. M3가 M1을 다시 쓰게 만들지 않기 위한 장치다. `docs/architecture.md`의 앵커 절 참조.

### 조명 유지

마을이 클레임 안의 어두운 지점을 찾아 횃불을 놓는다. `BuildOp` 큐를 그대로 쓴다.

L2에서는 조명 수준(`s.lightingScore`)이 숫자로 위협 계산에 들어간다.

## 경보 상태 머신

주민 개인이 각자 판단하면 절반은 싸우고 절반은 도망친다. **마을이 상태를 갖고 주민은 그것을 따른다.**

```
PEACE ──▶ ALERT ──▶ COMBAT ──▶ ROUT
  ◀────────  ◀────────  ◀────────
```

| 상태 | 전이 조건 | 주민 행동 |
|---|---|---|
| `PEACE` | 기본 | 일상 작업 |
| `ALERT` | 감시 시야에 적대 개체 / 플레이어가 종을 울림 | 민병대 무장, 성문 폐쇄, 비전투원 중심으로 이동 |
| `COMBAT` | 적이 클레임 내부 진입 / 주민 피격 | 민병대 교전, 비전투원 실내 |
| `ROUT` | 민병대 손실 > `routThreshold` (기본 0.5) | 전원 도주. 마을이 버려질 수 있음 |

복귀는 **역방향으로 한 단계씩**, 위협 소멸 후 `alertCooldownTicks`(기본 1200 = 60초) 경과가 조건이다.

`ROUT`이 반드시 있어야 한다. 마을은 전멸하는 게 아니라 **버려질 수 있어야** 한다. 주민이 흩어지고, 나중에 돌아와 재건하거나 영영 폐허로 남는다. "어느 날 다 죽어있음"보다 훨씬 나은 결말이다.

## 위협 감지 — 전방위 스캔 금지

클레임 전체에 AABB를 걸고 적대 개체를 찾으면 규모에 비례해 비용이 폭증한다.

**감시 지점만 스캔한다.**

- 감시탑(`WATCHTOWER` 플롯), 성문(`GateNode`), 순찰 중인 민병대
- 각자 반경 `watchRadius`(기본 32)만
- `watchIntervalTicks`(기본 20)에 한 번
- 개수는 `maxWatchPoints`(기본 6)로 상한

M1에서는 감시탑도 성문도 없으므로 `AnchorSet.watchPoints`가 **종 + 가장 바깥쪽 거주 지점**을 쓴다. 비용이 감시 지점 수에 비례한다는 성질은 그대로 지켜진다.

비용이 마을 크기가 아니라 감시 지점 수에 비례한다. 덤으로 **감시탑이 게임적 의미를 갖는다.** 탑이 없으면 적이 성벽 앞에 올 때까지 발견되지 않는다.

### L2에서의 위협

엔티티가 없으므로 위협은 **확률 이벤트**다. 스폰을 흉내 내지 말고 결과만 굴린다.

```java
int threatLevel(Settlement s, RandomSource rng) {
    int base = biomeDanger(s.center())          // 바이옴 위험도
             + structureProximity(s.center())   // 근처 요새·전초기지
             - s.lightingScore() / 2            // 조명
             + moonPhaseBonus();
    return Math.max(0, base + Mth.nextInt(rng, -3, 3));
}
```

`raidChancePerStep`(기본 0.002) 확률로 습격 이벤트가 발생하고, 발생하면 아래 공식으로 해소한다.

**스텝 단위 확률은 직관을 배신한다.** 1 게임일 = 24000틱 = 120스텝이다. 0.02로 두면 하루 기대 습격이 2.4회, 하루 안에 한 번이라도 털릴 확률이 91%다. 마을은 절대 자라지 못한다.

| `raidChancePerStep` | 게임일당 기대 습격 |
|---|---|
| 0.02 | 2.4회 |
| 0.005 | 0.6회 |
| **0.002** | **0.24회 (약 4일에 한 번)** |
| 0.0005 | 0.06회 (약 17일에 한 번) |

config에 확률을 넣을 때는 **항상 게임일 환산값을 주석으로 적는다.** 이 함정은 반복해서 밟게 된다.

## 민병대 — 엔티티 교체로 구현한다

바닐라 `Villager`를 전투원으로 만들려면 브레인을 뜯어야 한다. `PANIC` 활동이 `HURT_BY` 메모리에 반응해 도망치도록 하드코딩되어 있고, `ATTACK_DAMAGE` 속성 자체가 없다. **26.2에서도 그대로다** — `Villager.createAttributes()`에 공격력이 없고 `Activity.PANIC` 브레인 패키지가 살아 있다 (다만 클래스가 `net.minecraft.world.entity.npc.villager.Villager`로 이동했다). Mixin으로 브레인 등록부를 갈아끼우는 건 가능하지만 버전마다 깨진다.

**데이터가 원본이므로 엔티티 타입을 바꿔버리면 된다.**

```java
void conscript(Resident r, ServerLevel level) {
    Entity old = manager.entityOf(r.id(), level);   // 런타임 바인딩 맵. r에는 entityId가 없다
    if (old == null) return;                        // VIRTUAL이면 데이터만 바꾸면 된다

    MilitiaEntity m = ModEntities.MILITIA.get().create(level);
    m.setData(ModAttachments.RESIDENT_ID, r.id()); // 같은 Resident 레코드를 가리킨다
    m.snapTo(old.position(), old.getYRot(), old.getXRot());
    m.equip(r.gear());

    manager.unbind(r.id());
    old.discard();                                  // 뷰만 버린다
    level.addFreshEntity(m);
    manager.bind(r.id(), m.getUUID());
}
```

`Resident`에 `entityId` 필드는 없다. 바인딩은 저장되지 않는 런타임 맵이다 (`docs/data-model.md`). 주민이 `VIRTUAL`이면 엔티티가 없으므로 징집은 **플래그 변경 한 줄**로 끝난다 — 이것이 L0/L2가 같은 코드를 쓰는 지점이다.

교체 순서도 중요하다. `discard()`를 먼저 하면 그 틱에 주민이 없는 상태가 생기고, 인구 집계가 한 틱 동안 어긋난다.

주민의 정체성은 `Resident`에 있지 엔티티에 있지 않으므로, 껍데기 교체는 다른 뷰로 갈아끼우는 일일 뿐이다. `MilitiaEntity`는 처음부터 전투용으로 설계된 커스텀 엔티티라 **Mixin이 한 줄도 필요 없다.**

### 시각적 튐 가리기

교체 순간이 눈에 띄지 않게 **무기고를 경유**시킨다.

`ALERT` 진입 → 민병대 후보가 무기고(`ARMORY` 플롯)로 이동 → 도착 시 장비 수령과 함께 교체. 안에서 바뀌므로 플레이어에게는 "무장하고 나왔다"로 보인다.

해제는 역순이다. `PEACE` 복귀 시 무기고에서 장비를 반납하고 `Villager`로 돌아간다.

## 성문은 바닐라가 열 수 있는 것으로 짓는다

철문은 주민이 열지 못한다. 레드스톤이 필요하고, 바닐라 길찾기는 철문을 **통과 불가 블록**으로 취급한다. 성문을 철문으로 만들면 `GateNode`를 등록해도 농부가 못 나간다.

V1의 성문은 **나무 문 또는 울타리 문**이다. `PathfindingMalus`가 이미 잡혀 있어 추가 작업이 거의 없다.

- `ALERT` 이상에서 문을 닫는다 — 좀비는 나무 문을 부술 수 있지만, 그게 오히려 옳다. 성벽 등급을 올릴 이유가 생긴다
- `STONE` 등급부터 철문 + 레버를 쓰고 싶어지는데, 그때는 **문 대신 성문 블록(커스텀)** 으로 간다. 주민 통과 판정을 우리가 정의할 수 있다. V1 범위 밖이다

## 장비는 실질 비용이다

민병대는 `Settlement.stock`에서 장비를 꺼낸다. 창고가 이미 숫자 맵이므로 추가 작업이 거의 없다.

- 재고의 **최상급 장비 기준으로 등급**이 정해진다. 철검이 3자루면 3명만 제대로 무장하고 나머지는 나무 도구를 든다
- **전사하면 장비가 재고에서 사라진다.** 전투에 실제 비용이 붙는다
- 무장할 장비가 아예 없으면 민병대 전환 자체가 불가능하고 전원 은신으로 간다

마지막 항목이 플레이어에게 명확한 레버를 준다. *마을이 자꾸 털린다 → 철검을 기부한다 → 눈에 띄게 달라진다.* 원래 느낀 무력감의 정반대 경험이다.

### 누구를 징집하는가

- `JobDef.militiaEligible`이 true인 직업만 (농부·나무꾼 O, 사서·성직자 X)
- 인구 대비 `militiaRatioCap`(기본 0.3) 상한. 전원 무장하면 생산이 멈추므로 트레이드오프가 생긴다
- `TOWN`부터 전업 `guard` 직업 해금. 항상 무장 상태, 생산하지 않고 식량만 먹는다 (상비군의 비용)

## L0와 L2가 다른 답을 내면 안 된다

플레이어가 있으면 진짜 전투가, 없으면 공식이 돈다. 두 결과가 체계적으로 다르면 플레이어가 학습해버린다. "내가 있으면 더 위험하다"거나 그 반대거나.

### 난이도가 첫 번째 관문이다

**평화로움에서는 L2 습격도 굴리지 않는다.** 적대 몹이 스폰되지 않으므로 L0에서 습격은 절대 일어날 수 없고, 그런데도 공식이 주민을 죽이면 두 절반이 **가장 눈에 띄는 방식으로** 다른 답을 내는 것이다. 평화로움으로 플레이하는 사람이 일어날 수 없는 습격으로 마을을 잃는다.

난이도는 `SimParams.hostilesExist`로 **값으로 들어온다.** 시뮬레이션은 레벨을 보지 않는다.

**양쪽이 같은 스칼라를 공유한다.**

```java
int defenseRating(Settlement s) {
    return militiaCount(s) * gearTier(s) * 2
         + s.wall().tier().ordinal() * 15
         + watchtowerCount(s) * 8
         + (s.alert() == COMBAT ? 10 : 0);
}
```

### L2 해소

> **정정 (M1 계측).** 위 형태는 `threat`가 `defenseRating`을 넘는 순간 확률이기를 멈춘다. 비율 1.25에서는 조건이 절대 참이 될 수 없어 마을이 **매번** 진다. `/placitum simulate raid 20 500`이 `repelled 0.0%`를 내놓았다 — 굴림이 아니라 판정문이다.
>
> 실제 구현은 `rating / (rating + threat)`을 쓰고 양 끝을 5~95%로 자른다. 순서는 그대로다(방어가 강할수록 더 자주 이긴다). 다만 열세인 마을이 **대체로 지되 가끔 버틴다.** 그 차이가 시뮬레이션과 선고를 가른다.

```java
double ratio = threat / (double) Math.max(1, defenseRating(s));
if (rng.nextDouble() > ratio) {
    // 격퇴. 경상자 약간
    casualties = (int) (ratio * militiaCount(s) * 0.3);
    chronicle.add(RAID_REPELLED, ...);
} else {
    // 패배. 사상자, 자원 약탈, 바깥 밭 손실
    casualties = (int) (ratio * militiaCount(s) * 0.7);
    lootStock(s, rng);
    chronicle.add(RAID_LOST, ...);
}
```

### L0 보정

L0에서 결과를 억지로 맞추지 않는다. 대신 **습격 규모를 같은 `threat` 값에서 도출**한다. 몬스터 수와 장비가 `threat`의 함수, 민병대 스탯이 `gearTier`의 함수다.

그다음은 계측이다. 같은 조건으로 L0 전투를 N회 돌려 생존율을 재고, L2 공식의 계수를 그 값에 맞춘다. **이건 유도할 수 없고 튜닝해야 하는 종류의 문제다.**

`/placitum simulate raid <threat> <n>` 명령어를 M1에서 만들어 둘 것. 튜닝 시간이 몇 배로 줄어든다.

## 바닐라 습격과의 관계

바닐라에도 습격(불길한 예감 → 약탈자 습격)이 있다. 두 시스템이 동시에 돌면 판정이 겹친다.

| 대상 | V1 처리 |
|---|---|
| 바닐라 약탈자 습격 (L0) | **그대로 둔다.** 약탈자도 `Monster`이므로 감시 지점이 이미 본다 — 특수 처리 없이 경보가 올라간다 |
| 바닐라 습격 중 L2 습격 굴림 | 억제한다. `alert != PEACE`인 동안 `raidChancePerStep` 적용 안 함 |
| 철 골렘 | 유지한다. `defenseRating`에 `golemCount * 12`로 포함 |

NeoForge 26.2에는 습격 시작 이벤트가 없다. 다행히 필요하지도 않다 — 위협 감지가 적대 개체를 세는 방식이라 약탈자가 자동으로 포함된다. 특수 경로가 하나 없는 쪽이 낫다.

바닐라 습격을 대체하지 않는 이유는 단순하다. 그건 이미 잘 동작하고, 플레이어가 기대하는 것이며, **우리 문제가 아니다.** 우리 문제는 "아무 일 없이 어느 날 다 죽어 있는 것"이다.

자세한 바닐라 상호작용은 `docs/vanilla-interop.md`.

## 로그아웃 악용 차단

전투 중에 마을이 L2로 내려가면 **습격을 취소하지 않는다.** 현재 상태(남은 적 수, 남은 민병대, 부상 정도)를 그대로 L2 공식에 넘겨 결말을 낸다.

도망쳐도 결과는 난다.

## 사망 처리

| 경로 | 처리 |
|---|---|
| L0 엔티티 사망 | 사망 이벤트 → `Resident` 제거 + 연대기 `DEATH(전투)` |
| L2 공식 사상자 | 레코드에서 제거 + 연대기 기록. 시체도 드롭도 없다 |

사망은 반드시 **원인과 함께** 기록된다. 원래 불만의 본질은 주민이 죽은 게 아니라 *왜 죽었는지 몰랐다*는 것이다. `docs/population.md`의 연대기·묘지 참조.
