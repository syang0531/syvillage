# 건설

원래 문제: **마을 규모(집 수)가 늘지 않는다.**

## 공통 파이프라인

성벽이든 집이든 밭이든 **같은 여섯 단계**를 지난다. 여기서 갈라지기 시작하면 세 벌의 코드를 유지하게 된다.

| 단계 | 하는 일 |
|---|---|
| `NEED` | `NeedsModule`이 부족을 감지 (침대 부족, 성벽 미비, 식량 부족) |
| `PLAN` | 템플릿 선택 + 부지 선정 → `Blueprint` |
| `RESERVE` | 셀 상태 `RESERVED`, 자재 예약 |
| `QUEUE` | `BuildRecipe` 확정. 지면 높이를 샘플링해 박제 (`groundProfile`) |
| `EXECUTE` | L0: 건축가가 실제 배치 / L2: `progress`만 증가 |
| `COMPLETE` | 셀 `BUILT`, 플롯 등록, 연대기 기록 |

**모든 판단은 PLAN과 QUEUE에 모인다.** EXECUTE는 리스트를 순회하는 것 외에 아무것도 하지 않는다. 기초 채우기, 나무 제거, 평탄화까지 전부 `BuildOp`로 만들어 `ops`에 넣어야 이 성질이 유지된다.

`ops`는 저장하지 않는다. `BuildRecipe`에서 **결정적으로 재전개**한다 (`docs/data-model.md`). 그래서 QUEUE 단계가 지면 높이를 샘플링해 `groundProfile`에 박제하는 것이 중요하다. 그 입력이 고정되어야 `expand(recipe)`가 몇 주 뒤에도 같은 목록을 낸다.

## progress가 L0와 L2를 잇는다

```java
// L2 (ConstructionModule) — 월드를 건드리지 않는다
job.progress = Math.min(job.opCount(), job.progress() + builders * OPS_PER_STEP);

// L0 (BuilderEntity)
level.setBlock(op.pos(), op.state(), 3);
job.progress++;
```

`opCount()`는 `expand(recipe).size()`이며 캐시한다. 상한을 씌우지 않으면 `progress`가 op 수를 넘어가고, replay가 인덱스 범위를 벗어난다.

promote 시 replay는 `ops[0..progress)`를 월드에 적용하는 것뿐이다. 이것이 원칙 2("가상 단계에서 월드를 건드리지 않는다")의 구현 전부다.

## 우선순위

`NeedsModule`이 여러 부족을 동시에 감지하면 이 순서로 발주한다.

1. 식량 (밭) — 기아는 즉사다
2. 주거 (집) — 수용력 병목
3. 방어 (성벽, 감시탑)
4. 생산 (작업장)
5. 편의 (묘지, 도로)

단 `AlertState != PEACE`이면 방어가 1순위로 올라간다.

## 성벽 — 첫 구현 대상

집보다 쉽다. 부지 선정도 내부 구조도 없고 둘레 추적 하나뿐인데 파이프라인은 동일하다. **여기서 replay 연출과 자재 소모를 검증한 뒤 집으로 간다.**

### 경로

`BUILT`·`ROAD` 셀 집합의 외곽선을 그대로 따라가면 들쭉날쭉한 오목 성벽이 나온다. **볼록 껍질 또는 바운딩 박스에 여유 1~2셀**을 준 형태를 쓴다. 단순하고 자라날 여유도 생긴다.

### 지형 규칙

| 인접 칸 높이차 | 처리 |
|---|---|
| 1 ~ 2 | 계단식으로 따라감 |
| 3 ~ 4 | 수직 세그먼트로 붙임 |
| 5 이상 | **생략.** 자연 절벽이 성벽 역할 |
| 물 | 생략 (다리 세그먼트는 나중에) |

마지막 두 규칙이 중요하다. **지형을 깎기 시작하면 플레이어 눈에 그리핑으로 보이고**, 산악 지대에서 자재 소모가 폭발한다.

### 등급

| `WallTier` | 재질 | 높이 | 해금 |
|---|---|---|---|
| `NONE` | — | — | — |
| `FENCE` | 나무 울타리 | 1.5 | `OUTPOST` |
| `PALISADE` | 통나무 방책 | 3 | `HAMLET` |
| `STONE` | 석벽 + 성가퀴 | 4 | `TOWN` |
| `RAMPART` | 성벽 + 망루 | 6 | `CITY` |

V1은 `PALISADE`까지만 구현해도 충분하다. 나머지는 M4에서.

### 문

`ROAD` 셀이 성벽 링을 관통하는 지점에 자동 생성된다.

**생성 즉시 `GateNode`를 길찾기 데이터에 등록할 것.** 누락하면 닫힌 철문 앞에서 농부가 영원히 서 있는다. 주민 길찾기는 성벽 링을 통과할 때 반드시 게이트 노드를 경유하도록 강제한다.

### 철거와 재건

확장하면 옛 성벽을 헐어야 한다. **이건 버그가 아니라 기능이다.** 확장에 실질 비용이 붙어 "성장 vs 방어" 긴장이 생긴다.

- 옛 성벽 recipe를 전개한 뒤 역연산(원래 블록으로 되돌리기)을 `pendingOps`에 넣는다. 원래 블록은 철거 시점에 읽어 op에 담는다 — 이건 단발 변경이라 저장한다
- 자재는 `wallSalvageRatio`(기본 0.5)만큼 회수. 전액이면 확장이 공짜, 0이면 아무도 확장하지 않는다

## 집

### 템플릿

`.nbt` 구조물을 데이터팩에서 로드하고 셀 규격으로 분류한다.

```
data/placitum/structures/house/cottage_1x1.nbt
data/placitum/structures/workshop/smithy_2x1.nbt
```

`StructureTemplate`이 회전을 기본 지원하므로 4방향 회전은 공짜다. **현관이 도로를 향하도록** 회전을 선택한다.

### 격자의 범위와 건축 반경은 다른 것이다

`PlotGrid.size`는 **클레임 반경**에서 나온다 (`PlotGrid.sizeForClaim`). 지도는 우리가 아는 땅 전체를 덮어야 하고, 그건 주민이 몇 명인지와 무관하다.

`ScaleTier.gridSize()`는 **건축 반경**이다. 부지 선정이 중심에서 그 거리 안에서만 고른다. 티어가 오르면 마을이 바깥으로 퍼진다.

이 둘을 하나로 묶으면 편입된 바닐라 마을이 자기 광장 크기의 격자를 받고 영영 아무것도 못 짓는다. `docs/open-questions.md` 3번에 실측 기록이 있다.

### 부지 선정

```java
Optional<CellPos> findSite(Settlement s, int w, int h) {
    return s.grid().cells().stream()
        .filter(c -> c.isFreeBlock(w, h))                    // 연속 FREE
        .filter(c -> c.adjacentToRoad())                     // 도로 접함
        .min(comparingInt(c -> c.distanceTo(s.center())));   // 중심에 가깝게
}
```

**도로 인접 조건이 없으면 마을이 무작위로 퍼진다.** 이 한 줄이 마을 모양을 결정한다.

### 다양성

두 가지로 낸다.

1. 최근에 쓴 템플릿의 선택 가중치를 낮춘다 (`recentTemplatePenalty`)
2. **바이옴별 블록 치환 맵**을 적용한다 — 참나무 → 가문비나무, 자갈길 → 사암

치환 맵 덕분에 템플릿 한 벌로 여러 바이옴을 커버할 수 있다. 제작 부담이 크게 준다. 바닐라 마을이 바이옴마다 달라 보이는 것도 대체로 같은 원리다.

```json
// data/placitum/biome_palette/desert.json
{
  "minecraft:oak_planks": "minecraft:sandstone",
  "minecraft:oak_log":    "minecraft:smooth_sandstone",
  "minecraft:cobblestone":"minecraft:cut_sandstone"
}
```

## 밭

가장 쉽다. 템플릿이 필요 없다. 9×9 절차 생성에 중앙 물 한 칸, 평탄도 확인이면 끝.

**배치 위치가 설계 결정이다.**

- 성벽 안 우선. 넘치면 바깥
- 바깥 밭은 습격 시 손실 대상에 포함

그러면 성벽 확장이 식량 안정성과 직결되고, `docs/population.md`의 고리에 방어가 한 번 더 엮인다.

## 도로

V1에서는 단순 규칙으로 충분하다. 지형 절삭이나 다리가 필요해지는 시점에 다시 본다.

- 마을 중심에서 십자로 고정
- 건물이 생길 때마다 그 건물까지 `ROAD` 셀 한 칸 연장

## 자재

`BuildJob` 생성 시 `stock`에서 차감 **예약**한다. 부족하면 채집 작업이 생성되고 나무꾼·광부가 처리한다. L2에서는 숫자만 오른다.

자재 부족은 실패가 아니라 `WAITING_MATERIALS` **대기 상태**다. 그리고 **반드시 플레이어에게 알린다.**

```
대장간 건설 대기 중 — 철괴 12개 부족
```

종 UI에 이게 뜨면 플레이어에게 개입할 명확한 이유가 생긴다. 원래 느낀 무력감의 정반대다.

## 건축가가 실제로 하는 일 (L0)

### 도달 범위

4블록 높이 벽을 서서 어떻게 놓는가.

`ops`를 Y 오름차순으로 정렬해둔 것이 대부분을 해결한다. 이미 쌓인 부분 위로 올라갈 수 있기 때문이다. 남는 것은:

- 도달 범위를 `builderReach`(기본 5.5)로 확대
- 그래도 못 닿는 op는 건너뛰고 나중에 재시도

**자동 비계는 V1에 과잉이다.** 설치와 철거를 관리해야 해서 버그 표면이 크게 늘어난다.

### 속도와 연출

`buildOpIntervalTicks` 기본 10 (0.5초에 블록 하나). 집 한 채가 약 4분. 지켜보기에 지루하지 않고 너무 순식간도 아니다.

팔 흔들기 애니메이션, 배치 소리, 파티클만 붙이면 충분히 그럴듯하다.

## 플레이어와 충돌할 때

### 짓다 만 건물을 부순 경우

매 op마다 검증하면 비싸다. `verifySampleEvery`(기본 16)개마다 한 번 샘플 검증하고, 어긋나면 그 지점부터 다시 놓는다.

플레이어가 계속 부수면 `maxRebuildAttempts`(기본 3) 후 그 부지를 `BLOCKED`로 표시하고 포기한다. 무한 루프가 안 생기고 플레이어의 의사도 존중된다.

### 플레이어 건축물 보호

마을은 **자기가 놓은 블록만 기억한다**(`BuildOp` 로그). 부지 검증 시 자연 생성 블록도 아니고 마을이 놓은 것도 아닌 블록이 있으면 `BLOCKED`.

완벽하진 않지만 실용적으로 충분하고, `/placitum plot block`으로 수동 금지를 얹으면 분쟁이 거의 사라진다.

### 플레이어가 직접 지어준 집

V1에서 자동 인식하지 않는다. `/placitum plot register`로 수동 등록만 지원한다. 자동 판정은 V1 범위 밖이다.
